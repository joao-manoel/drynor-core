# Gamevals: 727 asset ids by their Jagex names

`gamevals/<type>.json` in the cache source tree (`cache-source/`, a git submodule - see
`docs/cache-source.md`) maps every **revision-727 cache id** of an asset type to
the Jagex developer name for that exact asset (`inv` 94 -> `worn`, `seq` 0 -> `swarm_walk`). They
were recovered once from the RS3-949 gameval tables (727 is version-locked and Jagex never
published gamevals for it, so this was reverse-engineered once); the rules a name had to clear
before it was written are in `gamevals/CONTRACT.md`.

**The catalogs are the artifact.** The one-time recovery tooling is gone and there is nothing to
re-run: the JSON files are canonical, hand-editable, and only ever improved in place. To rename an
asset, edit `gamevals/<type>.json` and rebuild - the typed constants are generated by the Gradle
build, which fails on a name conflict. This document covers how the server reads them and how the
constants are generated.

## Catalog shape

```json
{
  "revision": 727, "type": "seq", "source": "...", "date": "2026-08-30",
  "coverage": { "cache_ids": 17000, "named": 12000, "placeholder": 5000 },
  "entries": { "0": "swarm_walk", "1": "swarm_attack", "17": "seq_17" }
}
```

- One file per type, filename stem = type name. Types: `obj npc loc seq spotanim enum struct
  param inv interface component clientscript varp varbit varc varcstr varclan varbitclan
  varclansetting varbitclansetting bas hitmark headbar cursor mapelement quest model graphic
  sound midi material fontmetrics idk overlay underlay mapscene skybox quickchatoption
  quickchatphrase worldmap` - all 40 exist. A missing file is still tolerated (treated as
  an empty catalog, see below), so a partial folder under `GAMEVAL_PATH` works.
- Every 727 asset type is covered. The last eight were added on 2026-09-01: seven of them
  (`idk overlay underlay mapscene skybox quickchatoption quickchatphrase`) have no name source in
  existence and are placeholder-only by design, and `worldmap` names 44 of its 45 world-map areas
  from the cache's own name hashes. `CONTRACT.md` records each one's id space and why.
- **Map squares have no catalog and never will.** Index 5 archive names are a formula, not a table:
  `m<rx>_<ry>` (terrain), `l<rx>_<ry>` (locations), `n<rx>_<ry>` (npc spawns), `um<rx>_<ry>` and
  `ul<rx>_<ry>` (underwater) - no separator between the letter and the first coordinate. Compose
  them with `world.gregs.voidps.cache.MapSquare`, which takes either `(regionX, regionY)` or a
  packed region id; see `docs/cache-archive-names.md`.
- Cache **archive** names are not gamevals and get no catalog: they address a JS5
  `(archive, file)` coordinate, not a type id. `docs/cache-archive-names.md` has the formulas
  (indices 5, 30, 31, 10), and `docs/reference/worldmap-cache-names.json` keeps the index-23
  world-map static-element names, which follow no formula.
- `entries` has **every id the 727 cache holds** for that type. Names are unique per type.
- `component.json` keys are `"<interfaceId>:<componentId>"` and names are
  `"<interfaceName>:<componentName>"`.
- `clientscript.json` names keep Jagex's `[category,name]` form.

### How confident is a name? The `brute` channel

Most names are proof-grade: a name-hash match against a ~6k-entry dictionary, a field-for-field
structural match at the same id, or an aligned clientscript witness — each with an expected
false-hit budget under 0.05 for a whole run. One channel, `brute`, is deliberately weaker. It
recovers a name by searching a very large generated dictionary against the 727 name hashes, where
a 32-bit hit alone is worthless, and then requires the hit to be the *unique* one in the whole
searched space **and** to be corroborated by the asset itself — for a clientscript, agreement
between the candidate's tokens and what the script actually references; for a graphic or a music
track, membership of the cheapest pre-specifiable region that could have generated the name. The
gate is calibrated against held-out real names and against negative-control runs on random target
hashes, so each catalog reports the measured number of its `brute` names expected to be wrong
(`coverage.brute_residual_false_expectation`; 0.14 for `clientscript`, 0.24 for `graphic`, 0.05
for `midi`). Treat `brute` names as very likely right rather than certain: `coverage.by_channel`
counts them separately. Full rules in `gamevals/CONTRACT.md`.

### The placeholder rule

An id with no proven name still has an entry, holding the placeholder `<type>_<id>`
(`loc_1234`, `spotanim_77`); clientscripts use `cs2_<id>` and components
`component_<iface>_<comp>`. **A placeholder is not a name.** The runtime API hides placeholders:
`name()` returns `null` for them, `id()` never resolves one, and `entries()` leaves them out.
`rawName()`, `allEntries()` and `isPlaceholder()` expose them when you really want the stored
string.

## Where the server reads them from

The folder named by `GAMEVAL_PATH` (`.env`), which defaults to `<CACHE_SOURCE_PATH>/gamevals` when a
cache source tree is configured and to `./cache-source/gamevals` (the submodule in a repo checkout)
otherwise. That folder is the **only** copy of the catalogs: nothing is bundled into a jar, so a
deployed server needs the tree (or at least its `gamevals/` directory) on disk - `docs/deploy.md`,
"The cache source tree". Edits there take effect on restart with no rebuild.

A catalog that is missing or unreadable (a half-saved edit, say) is treated as empty:
one warning is logged for that type and the file is re-examined after 30 seconds. Catalogs are
parsed lazily on first use and cached per type; `Gameval.reload()` drops the cache.

## Runtime API

`org.drynor.core.gameval.Gameval` (in `core`) is the process-wide lookup. It is an instance of
`GamevalCatalog`, which can also be constructed against any folder (tests do).

```kotlin
import org.drynor.core.gameval.Gameval

val worn = Gameval.requireId(Gameval.INV, "worn")     // Int; throws if the name is unknown
Gameval.name(Gameval.SEQ, 0)                          // "swarm_walk", or null for unknown/placeholder
Gameval.label(Gameval.NPC, 1)                         // "name (1)" or "1", for logs and UIs
Gameval.id(Gameval.LOC, "tree")                       // Int?, placeholders never match
Gameval.has(Gameval.QUEST)                            // catalog present and non-empty
Gameval.entries(Gameval.OBJ)                          // Map<Int, String> of named ids only
Gameval.allEntries(Gameval.OBJ)                       // placeholders included
Gameval.rawName(Gameval.OBJ, 4151) / Gameval.isPlaceholder(Gameval.OBJ, 4151)
Gameval.source(Gameval.OBJ)                           // FOLDER or MISSING
```

Type constants: `OBJ NPC LOC SEQ SPOTANIM ENUM STRUCT PARAM INV INTERFACE COMPONENT CLIENTSCRIPT
VARP VARBIT VARC VARCSTR VARCLAN VARBITCLAN VARCLANSETTING VARBITCLANSETTING BAS HITMARK HEADBAR
CURSOR MAPELEMENT QUEST MODEL GRAPHIC SOUND MIDI MATERIAL FONTMETRICS IDK OVERLAY UNDERLAY
MAPSCENE SKYBOX QUICKCHATOPTION QUICKCHATPHRASE WORLDMAP`, and `Gameval.TYPES` lists them all.

Components are addressed by the packed id the interface packets use, `(iface shl 16) or comp`:

```kotlin
Gameval.component(679, 0)                              // "inventory:inv" or null
Gameval.component(packed)                              // same, from a packed id
Gameval.componentLabel(679, 0)                         // "inventory:inv (679:0)" or "679:0"
Gameval.componentId("inventory:inv")                   // packed Int?  (requireComponentId throws)
GamevalCatalog.pack(iface, comp) / ifaceOf(packed) / compOf(packed)
```

`GamevalCatalog.placeholder(type, key)` builds the placeholder string for an id, for code that
needs to recognise one outside the catalog (the codegen does).

`SeqGamevalAdapter` is the consuming half of the seq names: a Gson `TypeAdapter` that reads a
seq field as either the raw id or its gameval name, and writes the name when the catalog has
one. `NPCCombatDefinitions` annotates its four animation fields with it, which is what lets
`data/npcs/combatdefs` carry `human_staff_pound` where it used to carry `413`.

## Typed constants

For code that names an asset directly, every catalog also becomes a class of compile-time
constants in `org.drynor.core.gameval.gen`, generated by the `:core:generateGamevalConstants`
Gradle task into `core/build/generated/sources/gameval/java` and compiled as part of `core`.
Nothing is committed. The syntax is the same from Kotlin and Java:

```kotlin
import org.drynor.core.gameval.gen.Obj
import org.drynor.core.gameval.gen.Component

player.inventory.add(Obj.coins, 1000)
player.anim(Seq.swarm_walk)
when (script) { Cs2.quicksort -> ... }
Component.inventory.inv                 // packed (679 shl 16) or 0, what the interface packets take
Component.inventory.IFACE               // 679
const val WORN = Inv.worn               // they are real constants: const val, when, annotations
Loc.loc_54321                           // an id with no proven name, under its placeholder
```

| catalog | class | example |
|---|---|---|
| obj | `Obj` | `Obj.coins` |
| npc | `Npc` | `Npc.hans` |
| loc | `Loc` | `Loc.mcannoncrateboy` |
| seq | `Seq` | `Seq.swarm_walk` |
| spotanim | `Spotanim` | `Spotanim.<name derived from its seq>` |
| enum / struct / param | `Enum` / `Struct` / `Param` | `Enum.<name>` |
| inv | `Inv` | `Inv.bank` |
| interface | `Interface` | `Interface.inventory` (interface id 679) |
| component | `Component` | `Component.inventory.inv` (packed id), `Component.inventory.IFACE` (interface id) |
| clientscript | `Cs2` | `Cs2.quicksort` for `[proc,quicksort]` |
| varp / varbit / varc / varcstr | `Varp` / `Varbit` / `Varc` / `Varcstr` | `Varp.<name>` |
| varclan / varbitclan / varclansetting / varbitclansetting | `Varclan` / `Varbitclan` / `Varclansetting` / `Varbitclansetting` | |
| bas / hitmark / headbar / cursor / mapelement / quest | `Bas` / `Hitmark` / `Headbar` / `Cursor` / `Mapelement` / `Quest` | |
| model / graphic / sound / midi / material / fontmetrics | `Model` / `Graphic` / `Sound` / `Midi` / `Material` / `Fontmetrics` | |
| worldmap | `Worldmap` | `Worldmap.taverley_dungeon` (world-map area id) |
| idk / overlay / underlay / mapscene / skybox / quickchatoption / quickchatphrase | `Idk` / `Overlay` / `Underlay` / `Mapscene` / `Skybox` / `Quickchatoption` / `Quickchatphrase` | no name source exists for these types, so every constant is a placeholder (`Idk.idk_17`) |

All 40 catalogs are generated, 355,373 constants in 44 files (`loc` and `model` each span three
shards; `component` nests 1,321 interface classes inside one file). A type is only skipped if its
class is removed from the generator's table - a *missing* catalog file fails the build rather than
silently deleting thousands of symbols.

Only interfaces the review process proved carbon copies are *named* (206 of 1321), so
`Component.inventory` and friends exist for those alone; the other 1,115 are
`Component.interface_<id>`, the 727 toplevel interface 548 among them. The older flat
`com.rs.engine.variables` constants that used to live in `world` were a separate, earlier
generation and have been **removed**: every caller was rewritten to these classes, id-for-id (an id
whose catalog entry was a placeholder was left as a raw int literal with a
`// <type>_<id> (legacy name: ..., unproven)` comment - those literals can now become placeholder
constants). Caution: legacy re-sync batches (the `docs/legacy-baseline.md` workflow)
may reintroduce `world/src/main/java/com/rs/engine/variables/` or imports of it; if one does,
migrate the new callers to these classes and delete the package again.

### Every id is a symbol, placeholders included

An id with no proven name still gets a constant, under its placeholder identifier: `Loc.loc_54321`,
`Cs2.cs2_5002`, `Component.interface_548.component_548_2`. Three consequences, all deliberate:

- **You can reference any 727 asset today.** There is no waiting for a name and no raw int
  literals in game code.
- **Renaming is a one-line JSON edit.** Put the real name in `gamevals/<type>.json`, rebuild, and
  the constant is renamed with it.
- **A stale call site stops compiling.** `Loc.loc_54321` disappearing is exactly the signal you
  want: the compiler points at every reference so it can be renamed, instead of an int silently
  meaning something else.

The runtime API is unchanged and still hides placeholders: `Gameval.name()` returns `null` for
them and `Gameval.id()` never resolves one. The constant is the *id*, so it is correct either way.

### Naming

- Identifiers keep Jagex's snake_case exactly. A name starting with a digit gets a leading
  underscore (`2h_sword` -> `_2h_sword`); any character that is not `[A-Za-z0-9_]` becomes `_`;
  a Java or Kotlin reserved word gets a trailing underscore (`class` -> `class_`, `val` ->
  `val_`); a name that is only underscores becomes `_<id>`. Every rewrite is listed in the header
  comment of the generated file, and the original dev-name is kept in a trailing comment on the
  constant.
- Clientscripts drop Jagex's `[category,name]` wrapper: `[proc,quicksort]` -> `Cs2.quicksort`.
  When the same bare name exists in more than one category, every one of them is emitted as
  `<category>_<name>` (`Cs2.proc_scrollbar_vertical`, `Cs2.clientscript_scrollbar_vertical`).
- `Component.<interface>.<component>` is the packed id `(iface shl 16) or comp`, and
  `Component.<interface>.IFACE` is the interface id; `IFACE` is uppercase so it can never collide
  with a Jagex name (a component actually called `IFACE` becomes `IFACE_`). An interface with no
  proven name is `Component.interface_<id>`, matching what `Interface` calls it.
- The class names `Enum` and `Interface` shadow `kotlin.Enum` / `java.lang.Enum` only where you
  import them. Kotlin: an explicit `import org.drynor.core.gameval.gen.Enum` wins over the default
  import. Java: import `Enum` by name, not with `gen.*` (a wildcard import leaves it ambiguous).

### The build fails on a bad catalog

Because every id is now a symbol, a name that is merely odd is no longer harmless. The generator
refuses to emit and fails the build - naming the type, the ids and the offending strings - when:

| the catalog says | why it cannot become constants |
|---|---|
| two ids share a name | two constants would collide, or one would be silently renamed |
| two names collide only after escaping (`big-tree` and `big_tree`) | same, one edit away from being invisible |
| a name is another id's placeholder (`loc` 5 named `loc_9`) | `Loc.loc_9` would mean 5, not 9 |
| a name is empty, whitespace-only or `null` | there is no identifier to emit |
| a name is not a JSON string | the catalog is damaged |
| an id is not an integer, or a component key is not `<iface>:<comp>` | the id cannot be addressed |
| a component name is neither `<iface>:<comp>` nor its own placeholder | the two halves cannot be separated |
| one interface is named two ways inside `component.json` | its nested class name would be ambiguous |
| `component.json` and `interface.json` disagree on an interface name | `Component.<x>` and `Interface.<x>` would diverge |
| `coverage.cache_ids` / `named` / `placeholder` disagree with the entries | an id went missing, or the block is stale; the message lists the missing ids when the id space is contiguous |
| a catalog file is missing or unparseable | thousands of symbols would vanish silently |

Every defect found in a catalog is reported at once, up to 20 per rule. Each rule has a test in
`buildSrc/src/test/kotlin/org/drynor/build/gameval/GamevalValidationTest.kt` that runs the real
Gradle task over a temporary catalog fixture and asserts it fails with a message naming the ids.

### Renaming an asset

The catalogs are hand-editable and are the only place a name lives. To name id 54321 of `loc`:

1. In `gamevals/loc.json`, change `"54321": "loc_54321"` to `"54321": "your_name"`.
2. Bump `coverage.named` and drop `coverage.placeholder` by one - they must agree with `entries`
   or the build fails.
3. `./gradlew build`. `Loc.loc_54321` becomes `Loc.your_name`, and every stale call site stops
   compiling so the compiler shows you each one.

A name must clear the same bar the recovered ones did - proof that the id and the name denote the
same asset, or leave the placeholder; `gamevals/CONTRACT.md` has the rules. The build refuses
duplicates, collisions after identifier escaping, a name that is another id's placeholder, an empty
name and a stale `coverage` block (table above), so a bad edit fails loudly.

At runtime nothing needs rebuilding: the catalogs are read from `GAMEVAL_PATH` on demand, so a
server restart picks up an edited catalog. Only the typed constants need the build, which reads the
same tree (`-Pdrynor.cacheSource=<path>` or `DRYNOR_CACHE_SOURCE` point it elsewhere than the
`cache-source/` submodule).

A decompiled clientscript project (`cs2 decompile-all`) carries the same names - `Obj.abyssal_whip`,
`varbit_dungeoneering_floor`, `function quicksort` - all derived from the catalogs, never a second
copy. Scripts are laid out by their gameval: `[proc,quicksort]` becomes `proc/quicksort.ts` with a
`// [proc,quicksort]` header, and that catalog entry - not a numeric id in the file - is what binds
the file to the archive it compiles into (placeholders live under `cs2/`). After editing a catalog, `./gradlew :tools:run --args="cs2 apply-names <dir>"` regenerates the
project's declaration files and rewrites every reference to the new name; any reference it cannot
rewrite fails `tsc` rather than compiling stale. The reverse direction also exists: rename a symbol
in the editor (plain F2 in VS Code - the id binding lives in a header or doc comment, not the name)
and `cs2 sync-names <dir>` writes the new name back into the catalog it came from, then re-derives
the project so the two cannot diverge. `cs2 check-names <dir>` reports divergence without changing
anything, and `cs2 compile` refuses a folder whose names contradict the catalogs instead of
guessing.

### Regenerating

Nothing to do: `./gradlew build` (anything that compiles `core`) regenerates the constants when a
catalog changed and skips the task otherwise. To run it alone:

```
./gradlew :core:generateGamevalConstants
```

The task is incremental and cacheable - `@InputFiles` the 40 catalogs, `@OutputDirectory` the
generated tree - and Gradle also hashes the generator's own classes, so editing `buildSrc` re-runs
it. A second build with nothing changed reports `UP-TO-DATE`. Output is deterministic (ascending
id, no timestamps) and a file is only rewritten when its content changes.

The generator lives in `buildSrc/src/main/kotlin/org/drynor/build/gameval/`:

| file | what it is |
|---|---|
| `Catalogs.kt` | the type -> class table, the placeholder rule, and the catalog reader (Groovy's `JsonSlurper` from the Gradle distribution - no external dependency, no network) |
| `Identifiers.kt` | the identifier rules and the reserved-word sets |
| `GamevalValidation.kt` | the checks above |
| `GamevalCodegen.kt` | the emitters (simple, clientscript, component) and the shard chain |
| `GenerateGamevalConstants.kt` | the Gradle task |

`./gradlew :buildSrc:test` runs `buildSrc`'s own tests on demand; no build runs them for you. `GamevalConstantsTest` in `core`
then cross-checks the *generated classes* against the catalogs on the classpath - every constant
is an id of its catalog, every id has a constant, unnamed ids resolve under their placeholder, and
every component is packed `(iface shl 16) or comp` under a class whose `IFACE` is its interface.

Reading `JsonSlurper` with its default parser is quadratic on a flat object this size (43 s for
`loc.json` alone); the reader asks for `JsonParserType.INDEX_OVERLAY`, which does the same file in
0.05 s. Keep that if you touch the reader.

### Editor autocomplete

The generated directory is registered on `core`'s main source set
(`sourceSets.main { java.srcDir(generateGamevalConstants) }`), so `compileJava` and `compileKotlin`
depend on the task and any Gradle-aware IDE indexes it as a source root. `core` also applies the
`idea` plugin and adds the directory to `idea.module.generatedSourceDirs`, which is what makes
IntelliJ mark it *generated* rather than hand-written on a Gradle import.

To verify in IntelliJ: run `./gradlew :core:generateGamevalConstants`, then **Reload All Gradle
Projects**. `core/build/generated/sources/gameval/java` shows as a source root with the generated
badge, and `Obj.` completes 25,355 members (`Loc.` completes through the `Loc -> Loc2 -> Loc3`
chain). If completion is empty, the task has not run yet - build once, or reload again.

### Why the generated files are Java, and how big types are sharded

The generator emits Java classes of `public static final int` fields rather than Kotlin
`object`s with `const val`s. Both give `Obj.coins` from Kotlin and from Java and both are inlined
compile-time constants, but the JVM's per-class limits and the compilers' behaviour differ. All
of the following was measured with the toolchain in this repo (Kotlin 2.3.0, javac 25):

| approach | per-class ceiling | measured | compile time |
|---|---|---|---|
| Kotlin `object { const val }` | constant pool: 2 entries per constant (name Utf8 + Integer) of 65535 | 32,740 ok, 33,000 and 40,000 fail with `ClassTooLargeException` | **130-160 s** for one 32k object |
| Kotlin `abstract class { @JvmField val }` chain under an `object` | constructor bytecode 64 KB (`aload_0; sipush/ldc; putfield` per field) | 9,000 ok, 10,000 fails with `MethodTooLargeException: <init>` | 19 s per 9k class; not static, not const |
| Kotlin extension properties (`val Loc.x get() = ..`) split over files | facade constant pool | 30,000 in one file fails; no limit across files | Kotlin `Loc.x` only; Java would need `LocKt.getX(Loc.INSTANCE)`; not const |
| **Java `public static final int` class chain** | constant pool: 2 entries per constant | 32,760 ok, 32,765 fails (`too many constants`) | **0.7 s** per 32k class with javac; the Kotlin compiler reads 70k such constants from Java sources in ~4 s |

`loc` and `model` have ~74k ids each in the 727 cache, so a single class cannot hold every id of
those types. The chosen layout keeps `Loc.<name>` for every name:

- The first 32,000 constants (by ascending id) live in the public class `Loc`; the rest continue
  in package-private classes `Loc2`, `Loc3`, ... and the chain is linked by inheritance,
  `Loc extends Loc2 extends Loc3`.
- Java inherits static fields through a subclass, so `Loc.<name>` resolves whichever shard holds
  it. Kotlin 2.x (K2) resolves static members of a Java class through a Java subclass as well,
  which was verified for a three-level chain from another package in `const val`, `when` branches
  and annotation arguments, all constant-folded in the bytecode. (This is exactly what a Kotlin
  `object` cannot do: Kotlin never inherits statics into a Kotlin type, so a `const val` object
  would have forced `Loc2.<name>` on callers for the overflow.)
- The shard size is 32,000 rather than the 32,760 ceiling to leave room for the class's own
  constant-pool entries; it is the task's `shardSize` input. Component classes are nested per
  interface (818 members at the largest) and never come near the limit.

Covering every id rather than only the named ones costs almost nothing. Measured here from an
empty `core/build`, warm daemons:

| | named ids only (149,287 constants) | every id (355,373 constants) |
|---|---|---|
| generated source | 9.5 MB, 42 files | 21 MB, 44 files |
| `:core:jar`, cold build dir | ~29 s | ~24 s (within noise of each other) |
| `core.jar` | 7.3 MB | 9.6 MB |

Per task, full coverage: `generateGamevalConstants` 2.5 s, `compileKotlin` 14.7 s, `compileJava`
4.8 s, `jar` 2.3 s. The equivalent Kotlin objects would have added several minutes to every clean
build.

The trade-off is only cosmetic: `Loc2`, `Loc3` are visible in the package's file list and to
Java code in that package, and their javadoc says to go through `Loc`.
